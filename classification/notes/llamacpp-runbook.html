Gemma 4 Extraction Runbook

Replacing the candle pipeline with llama.cpp serving Gemma 4 E4B at q4_0, single pass, text only. Every number here was measured on a Ryzen 9 7950X3D at 16 threads; the target is a Xeon Gold 6210U.

1

What you are deploying

One model file. The vision projector is only needed if you later attach images.
FileSourceSizeNeeded

This is Google's quantization-aware-trained release, not a community post-training quant. It is why q4_0 holds up: the model was trained with 4-bit weights in the loop. Do not swap it for a generic Q4_K_M expecting an upgrade.

Distribution: your call

No size constraint forces this either way. 4.8 GB is well under what registries allow: DigitalOcean permits 20 GB per layer, Fly.io 8 GiB, and the OCI spec sets no layer limit at all.

Bake it into the image when deploys are infrequent and nodes are long-lived. The file never changes, so as its own layer it is pulled once and cached, the deploy stays one artifact, and the model cannot drift out of step with the code.

Mount a volume when you want small CI pushes and cheap registry storage, or expect to swap models without rebuilding. The cost is that you own the fetch, the verification, and the failure mode where the volume is empty or holds the wrong file.

For a single long-lived box, baking it in is the simpler answer. Verify the checksum either way; it is cheap insurance on a 4.8 GB download however it arrives. If you do fetch at deploy time across several nodes, mirror it internally rather than hitting Hugging Face in parallel.

Building llama.cpp for Cascade Lake

Pinned at 56b9eb2 (2026-09-12) for these results. Build on the target and let it detect, or set the ISA explicitly when cross-building.

# on the 6210U itself
cmake -B build -DCMAKE_BUILD_TYPE=Release -DGGML_NATIVE=ON -DLLAMA_CURL=OFF
cmake --build build -j "$(nproc)" --target llama-server

# cross-building, or pinning the ISA for a reproducible image
cmake -B build -DCMAKE_BUILD_TYPE=Release -DGGML_NATIVE=OFF \
  -DGGML_AVX512=ON -DGGML_AVX512_VNNI=ON -DGGML_AVX512_VBMI=OFF \
  -DGGML_AVX512_BF=OFF -DLLAMA_CURL=OFF

Cascade Lake has avx512f/dq/cd/bw/vl and avx512_vnni. It does not have avx512_bf16 (Cooper Lake) or AMX (Sapphire Rapids). Enabling either produces an illegal instruction at runtime, not a build error.

VNNI is the flag that matters for you. The q4_0 dot product at ggml/src/ggml-cpu/arch/x86/quants.c:106 uses _mm256_dpbusd_epi32 when __AVX512VNNI__ && __AVX512VL__ are defined, and falls back to a slower two-instruction path otherwise.

3

Running the server

llama-server \
  -m /srv/models/gemma-4-E4B_q4_0-it.gguf \
  --host 127.0.0.1 --port 8081 \
  -c 4096 -np 1 \
  -t 20 -tb 20 \
  --jinja --reasoning off \
  --sleep-idle-seconds 120 \
  --no-warmup
Why each flag is there.
FlagReason
-c 4096Context per slot. Your longest text-only prompt measured 2,440 tokens (Defensive Network). 4096 leaves headroom; going higher costs KV cache for nothing.
-np 1Server slots. Default is auto and picked 4, which multiplies KV cache by four. One slot is right for a sequential actor; raise it only if you send concurrent requests.
-t 20 -tb 20Physical cores, not threads. The 6210U is 20C/40T — hyperthreads hurt on memory-bound decode. -tb covers prompt processing separately.
--jinjaUses the model's own chat template from the GGUF. Gemma 4's turn markers are <|turn> and <turn|>, not Gemma 3's <start_of_turn>.
--reasoning offGemma 4 reasons before answering. Left on it spent 895 tokens reaching a 51-token answer, and a token cap truncates it mid-thought leaving content empty.
--sleep-idle-secondsReleases the model after idle. See below — it is the single biggest resource win for a workload that runs in bursts.
--no-warmupSkips a dummy decode at boot. Drop it if you would rather pay that cost at startup than on the first request.

Measured at these settings: 7.13 GiB resident after load, 7.24 GiB after a request, 273 tok/s prompt and 19.3 tok/s generation on a 2,440 token prompt. Startup to healthy is a few seconds from warm page cache.

4

Idle memory: sleep the model

Your classifier runs in bursts and then sits idle, and a resident 7 GiB the rest of the time is pure waste. --sleep-idle-seconds N releases the model after N seconds with no work, and reloads it transparently on the next request.

Measured with --sleep-idle-seconds 20, same prompt each time, prompt cache disabled.
StateRSSRequest wall time
Loaded, awake7.13–7.27 GiB16.05 s
Asleep0.18 GiB—
First request after sleepback to 7.27 GiB17.38 s

A 1.34 second wake penalty to give back 7 GiB. For anything but a continuously saturated queue that is an easy trade, and it is cheap because the weights are mmapped — waking is page faults, not a re-read and re-parse of the GGUF.

Set the threshold above your natural gap between items so a batch does not sleep mid-run. 120 seconds is a reasonable start; log the wake events and tune from there. The server writes entering sleeping state when it drops the model.

Related

--models-dir with --models-max runs the server in router mode, loading and evicting several models on demand. Overkill for one model, but the mechanism to reach for if you ever serve extraction and a transcription model from one host.

5

The request

Post to /v1/chat/completions. One user message holding the populated prompt, and a schema that constrains decoding.

{
  "messages": [{ "role": "user", "content": "<prompts/features.txt, populated>" }],
  "temperature": 0.0,
  "max_tokens": 512,
  "response_format": {
    "type": "json_schema",
    "json_schema": {
      "name": "features",
      "strict": true,
      "schema": {
        "type": "object",
        "properties": {
          "types":    { "type": "array", "items": { "type": "string" } },
          "features": { "type": "array", "items": { "type": "string" } }
        },
        "required": ["types", "features"],
        "additionalProperties": false
      }
    }
  }
}

The schema is compiled to a GBNF grammar and applied during sampling, so a markdown fence is not a reachable token. This is the part that lets you delete sanitise_output rather than fix it: malformed JSON stops being possible, including the truncated-object case that makes it panic at classification/src/lib.rs:245.

Do not do this in the prompt

Appending “respond with the JSON object only, no markdown” also removes the fences, but the model reads it as an instruction to be brief. One item dropped from 16 features to 2, and output from 148 tokens to 22. A milder wording cost exactly the same. Use the grammar.

genres.txt is the same shape with genres and themes as the two array fields.

Tuning, in the order worth trying

KnobEffectMeasured
-t / -tbPhysical cores first. Test 20 against 40 on the target; decode is memory-bound and hyperthreads often lose.—
-np with -cbIf you batch many items, more slots with continuous batching raises throughput at the cost of KV memory per slot.—
-cLower is cheaper. 4096 fits text-only comfortably; images or transcripts need 8192–16384.2,440 tok max
-ctk / -ctv q8_0Quantized KV cache. Only worth it if you raise context a long way.—
-fa onFlash attention. Defaults to auto; pin it if you benchmark a difference.—
QuantizationQ8_0 is 7.48 GiB and stays on the VNNI path. Only test it if you suspect q4_0 quality; QAT makes that unlikely.4.80 → 7.48 GiB

Do not port the BF16 numbers from the bench. BF16 was faster at prompt processing here because this Zen 4 chip has avx512_bf16; on Cascade Lake those ops widen to F32 and the advantage disappears. The q4_0 figures are the ones that transfer, because the integer path is identical on both chips. Absolute throughput still will not match: the 6210U has six memory channels against this desktop's two, and on a bandwidth-bound decode that may well favour the Xeon.

8

Things that will bite

  • Gemma 4's stop token is <turn|> (id 106), not <end_of_turn>, which is not in its vocabulary at all. Only relevant if you bypass the server; --jinja handles it.
  • An empty content with finish_reason: length means reasoning ate the budget. Check --reasoning off is set.
  • The old 100,000 token cap at runner.rs:80 should not come back. 256 covers every observed answer; Defensive Network's 186 is the high-water mark, and a cap that large turns one bad generation into an overnight hang.
  • Keep raw responses. Log the model's answer before parsing. Every useful diagnosis in the benchmark came from having the unmodified text.
  • Attaching the preview image is not worth it. It costs roughly 280 prompt tokens and made extractions shorter and more generic across every item tested. The vision path works — it read version tags, CJK glyphs and 8-pixel name labels — but the picture dilutes a description that already carries the content.
  • If you revisit images later, transcribe them in a separate call and append the text to the description. Attaching them to the extraction prompt does nothing at all: 0 of 15 marker terms whether six images were attached or none.
Measured on llama.cpp 56b9eb2 with google/gemma-4-E4B-it-qat-q4_0-gguf, Ryzen 9 7950X3D at 16 threads, five RimWorld workshop items across two extraction prompts. Raw runs are in bench-out-llamacpp/ and bench-out-promptv2/.
